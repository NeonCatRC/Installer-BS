# Installer-BS — дорожная карта (Фаза 1 / Фаза 2)

Продолжение `PLAN.md` (мастер). Фиксирует **разделение «формат vs GUI»** и раскладывает улучшения по
фазам и трекам. Источник правды — здесь; правим документ, а не память агентов. Фаза 0 (GUI rich-TUI,
реализована) — §6 ниже (заменяет прежний `GUI-PLAN.md`).

## 0. Зафиксированные решения (согласовано с пользователем 2026-06-26)

- **Структура — A2 (монорепо, промоут GUI).** `examples/bs-gui` → `apps/installer-bs-gui/`. Ядро
  (`bs` + `lib/` + `template/` + `locales/`) и GUI — два **независимых продукта в одном репо**, со
  своими версиями и релиз-циклами.
- **Дистрибуция GUI — отдельный GitHub-релиз.** Код в `apps/`; готовый `installer-bs-gui-X.Y-any.bs`
  публикуется как **ассет релиза** (тег `bs-gui-X.Y`, отдельно от релизов ядра). `README.md` ведёт на
  страницу Releases (скачать один файл), а не на ветку. Релиз — иммутабельная пиннутая поставка: его
  `.bs` забандлил ядро из того же дерева на момент тега (провенанс = тег/коммит) — см.
  [ARCHITECTURE «Модель версий и пин»](../ARCHITECTURE.md).
- **zenity выкидываем.** Полноценный rich-TUI закрывает потребность в оконном бэкенде — оставлять GTK-зависимый
  путь незачем. См. WP-G1.0.
- **Нейминг — B1 (umbrella).** «Installer-BS» = зонтик-проект. Внутри:
  - **формат + CLI** = `bs` / `.bs` («формат Installer-BS»);
  - **GUI-утилита** = «**Installer-BS Manager**» (бинарь/id `installer-bs-gui` оставляем стабильным).
- **Порядок Фазы 1 — формат/CLI вперёд**, GUI-track следом (кроме дешёвого долга `/`-фильтра и выпила zenity).

### Карта имён (claim == repo)

| Сущность | Имя для пользователя | Тех-id |
|---|---|---|
| Проект / репо / лицензия | Installer-BS | `Installer-BS` |
| Формат пакета | формат `.bs` (Installer-BS format) | `.bs`, `format_version` |

### Целевое дерево (после миграции)

```
Installer-BS/
├── bs, lib/, template/, locales/   # ЯДРО: формат + CLI (своя версия, тег bs-core-vX.Y)
├── apps/
│   └── installer-bs-gui/           # GUI «Installer-BS Manager» (своя версия, релиз bs-gui-X.Y)
│       ├── app/{installer-bs-gui,installer-bs.svg}
│       ├── recipe                  # бандлит ядро из того же дерева
│       └── README.md
├── examples/                       # hello, greeter, xonotic (демо формата)
├── tests/                          # lint.sh, e2e.sh
├── docs/                           # спека, архитектура, музей, dev/
└── README.md                       # формат+CLI; секция «GUI → страница Releases»
```

Монорепо: recipe GUI бандлит `bs`+`lib`+`template`+`locales` из того же дерева. Пин — это **тег релиза**
GUI (`bs-gui-X.Y`): его `.bs`-ассет иммутабелен и несёт ядро на момент тега. Распространение — один файл
со страницы Releases, без клонирования репо.

### Версионирование (три независимых)

- **format_version** — целое в манифесте (текущее = `1`). Растёт при изменении контракта формата.
- **bs (CLI)** — свой semver. `bs version` печатает версию CLI.
- **installer-bs-gui** — своя версия (сейчас `0.3.0`), свой релиз-цикл.

## 1. Трек ФОРМАТ + CLI (`bs`)

### Фаза 1 — зрелость формата и доверия

**WP-F1.1 — `format_version` + политика совместимости**
- **Вход:** `template/stub.sh`, `lib/manifest.sh`, `lib/pack.sh`, `docs/PACKAGE-FORMAT.md`.
- **Выход:** сборщик пишет `format_version=1` в манифест + шапку пакета; рантайм сравнивает: пакет
  требует версию выше, чем умеет рантайм → внятный отказ (как арх-страж), обход `BS_NO_FORMAT_CHECK=1`.
  Политика: добавление **опциональных** полей назад-совместимо (версию не бампаем); несовместимое
  изменение контракта → bump major + отказ старых рантаймов.
- **DoD:** пакет с `format_version=99` отвергается понятным сообщением; обычные пакеты несут `=1`;
  `--info` его печатает; e2e-кейс; shellcheck/lint зелёные.

**WP-F1.2 — Trust / keyring UX**
- **Вход:** `lib/sign.sh`, `bs verify`.
- **Выход:** `bs trust <fpr|file>` (импорт в **проектный** keyring `$XDG_DATA_HOME/installer-bs/trust/`),
  `bs keys` (список доверенных), **TOFU** при первом `verify` неизвестного ключа в TTY (показать fpr,
  спросить; `--trust`/`--yes` для скриптов). `verify` ищет в проектном keyring, не лезет в глобальный GPG.
- **DoD:** sign → `bs trust` → `verify` зелёный без глобального импорта; незнакомый ключ → TOFU-промпт;
  tampered → fail; не-TTY без `--trust` → отказ (не молчаливое доверие); e2e.

**WP-F1.3 — Финализация спеки `docs/PACKAGE-FORMAT.md`**
- **Вход:** текущая спека + все v0.3-поля (`extra_exec`, `mime_types`, `icon`/`icon_size`, `build_id`,
  `source_type`, `bash_completion`, `isolate_home`…).
- **Выход:** таблица полей (обязательные/опц., тип, дефолт, пример); раздел `format_version`; sidecar-файлы
  (`.sha256`/`.sig`); формат маркера payload; режимы стаба. **Сверка с кодом**: каждое поле в коде описано,
  каждое поле в доке существует в коде — ноль «придуманных».
- **DoD:** диф спека↔код пуст; ревью пользователем.

**WP-F1.4 — bats-юниты + CI (долг WP6 из AGENT-TASKS)**
- **Выход:** bats на `manifest::parse` (инъекция, обязательные поля), арх-детект, dispatch;
  `.github/workflows/ci.yml` гоняет `tests/lint.sh` + `tests/e2e.sh` на `ubuntu-latest`
  (ставит shellcheck/zenity/xvfb/python3). Опц. бейдж статуса.
- **DoD:** CI зелёный на push; bats локально зелёные.

### Фаза 2 — мультиарх и дистрибуция (с явными границами)

**WP-F2.1 — `bs install <url|path>` (разовая установка, НЕ репозиторий)**
- Скачать `.bs` (+ `.sig`/`.sha256` рядом), проверить (keyring из F1.2), `--install`.
  Контент-адресуемый кэш скачек (как у рецептов), `BS_NO_FETCH_CACHE` уважается.
- **Граница:** это установка по **явному URL**, не index/discovery (тот отвергнут, PLAN §8).
- **DoD:** `bs install file://…/x.bs` и `https://…` ставят с проверкой; битая подпись/сумма → отказ; e2e
  с локальным http-сервером.

**WP-F2.2 — честный `bs build --fat` (Музей, Зал 5)**
- Мультиарх payload + таблица «арх→offset»; страж выбирает ветку по `uname -m`; `exec` правильной.
  **Только по флагу**, с честным дисклеймером в выводе («да, это ровно то, над чем мы смеёмся; вот когда
  оправдано»).
- **DoD:** fat-пакет с 2 «арх» запускает правильную; `--info` печатает таблицу; обычный (не-fat) не меняется.

**WP-F2.3 — релиз-автоматизация / провенанс**
- Подпись в CI (ключ — секрет окружения); артефакты релиза `.bs` + `.sig` + `.sha256`. Опц. SBOM-список
  бандл-`.so` + их источников (`bs verify --provenance`).
- **DoD:** тег → CI собирает, подписывает, прикладывает артефакты; verify зелёный на скачанном.

## 2. Трек GUI (Installer-BS Manager)

### Фаза 1 — GUI как продукт

- **WP-G1.0 — выпил zenity-бэкенда.** Полноценный rich-TUI делает оконный zenity необязательным.
  Удалить ветку `zenity` в `ui_*`, `zen()`, выбор `UI=zenity`; путь «дисплей есть, но двойной клик» →
  переоткрытие в терминале (rich-TUI). Обновить README-секцию «почему не бандлим GUI» → «TUI
  самодостаточен, отдельное окно не нужно».
  - **DoD:** в лаунчере нет упоминаний zenity; pty-матрица зелёная; двойной клик без терминала →
    reopen-in-terminal; shellcheck/lint.
- **WP-G1.1 — фильтр `/` в списках** (долг Phase 0, шаг 6). Побайтный substring по меткам (UTF-8 ok).
- **WP-G1.2 — «Собрать .bs из рецепта»** — выбор рецепта, `bs make`/`sign` с живым логом (`ui_run_log`
  уже готов; дописать пункт меню и flow).
- **WP-G1.3 — расширенный installed-вид** — размер / дата / источник / статус подписи; действие
  «Проверить подпись / доверять» (поверх F1.2).
- **WP-G1.4 — прогресс долгих операций** (xonotic ~1 ГБ): спиннер/проценты в `ui_run_log`.

### Фаза 2 — упаковка и UX

- **WP-G2.1 — MIME-ассоциация `.bs`** → открывать Manager двойным кликом (`mime_types` в его манифесте +
  обработка `"$1"` как пути в лаунчере).
- **WP-G2.2 — конфиг GUI** `$XDG_CONFIG_HOME/installer-bs/`: язык, тема, дефолт-tier (rich/plain).
- **WP-G2.3 — тема / ASCII-only режим** для совсем дохлых TERM.

## 4. Границы (что НЕ делаем без отдельного решения)

- **Репозиторий / `bs index` / discovery** — отвергнут как scope-creep (PLAN §8). `bs install URL` (F2.1) —
  это *установка по явному адресу*, не каталог. Любой шаг к discovery — отдельное явное решение.
- **Бандл GTK ради GUI** — нет (Музей-смех). После выпила zenity (WP-G1.0) оконного режима нет вовсе:
  UI самодостаточен в терминале (rich-TUI), окна не требуется.
- **qemu / bwrap / sandbox** — нет (PLAN §1.7: только бандлинг `.so`).

## 6. Фаза 0 — GUI rich-TUI (ВЫПОЛНЕНА)

Заменяет прежний `GUI-PLAN.md`. tui-ветка лаунчера переписана в самопальный «dialog» (без Go,
zero-dep, `arch=any`):

- **движок:** raw-режим (`stty`), trap-восстановление на EXIT/INT/TERM/HUP, ридер клавиш с
  ESC-дизамбигуацией (`-t 0.05`), дисплей-ширина в **кодпойнтах** (разбор UTF-8 под `LC_ALL=C` —
  кириллица не рвёт рамку), frame/draw-хелперы, alt-screen;
- **примитивы:** `tui_menu` (стрелки/инверсия/скролл/счётчик `i/N`/полоса `▲┃▼`), `tui_confirm` (←→,
  дефолт «Нет»), `tui_message`, `tui_run_log`, `tui_pick_file` (raw↔canonical для `read -e`);
- **ресайз** SIGWINCH (trap + поллинг размера в ридере), **`NO_COLOR`**, **plain-фолбэк** (старое
  нумерованное меню; `tui_capable`/`BS_GUI_PLAIN=1`). zenity-ветка ещё на месте — снимается в WP-G1.0.

Проверено в Docker (`bs-test`): shellcheck-clean; pty-матрица (нав/скролл/confirm/run_log/pick_file/
ресайз/NO_COLOR/plain/restore terminal); сборка `.bs` ~48 KiB; e2e install/uninstall; `tests/lint.sh`
(lint ok) + `tests/e2e.sh` (62/0). Деталь движка — в коде + [ARCHITECTURE](../ARCHITECTURE.md).
