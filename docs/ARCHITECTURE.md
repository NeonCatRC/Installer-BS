# Архитектура Installer-BS

Для контрибьюторов. Правила кода и стиля — в [`docs/dev/GUIDELINES.md`](dev/GUIDELINES.md).
Формат пакета — в [`docs/PACKAGE-FORMAT.md`](PACKAGE-FORMAT.md). Дорожная карта — в
[`docs/dev/ROADMAP.md`](dev/ROADMAP.md).

«Installer-BS» — зонтик. Внутри два независимых продукта:

- **формат `.bs` + CLI `bs`** — ядро: формат, рантайм, сборщик, реестр, подпись;
- **Installer-BS Manager** (GUI) — в `apps/installer-bs-gui/` (монорепо), поставляется отдельным
  GitHub-релизом; его `.bs`-ассет бандлит **пиннутую** (тегом релиза) версию ядра — см. ниже.

## Карта (ядро)

```
bs                      точка входа: резолвит свой каталог, source модулей, core::dispatch "$@"
lib/
  core.sh               детект платформы (единственный), разбор глобальных флагов, диспетчер команд
  ui.sh                 вывод (цвет авто-гаснет вне TTY/NO_COLOR), info/ok/warn/error, confirm
  i18n.sh               загрузка локали по $LANG, английский — фолбэк-база; i18n::t по ключу
  manifest.sh           парсер манифеста как ДАННЫХ (без eval/source) + валидация
  pack.sh               `bs build`: каталог + манифест -> .bs
  bundle.sh             сбор .so через ldd (ELF, нативный хост), exclude базового libc/loader
  recipe.sh             `bs make`: рецепт (source_type tar/zip/deb) -> staging -> pack
  sign.sh               OpenPGP sign/verify (gpg), sidecar `.sig`; `bs --check` без вшитого хэша
  installed.sh          реестр: `bs list` / `bs info <name>` / `bs uninstall <name>` по manifest+.bs-files
  platform/linux.sh     платформо-специфика за тонким интерфейсом (BSD доложить отдельным модулем)
locales/{en,ru}.sh      таблицы строк (ассоциативные массивы)
template/stub.sh        раннтайм пакета: префиксится к payload при сборке
examples/               hello / greeter (бандл .so) / xonotic (рецепт) — примеры формата
tests/{lint.sh,e2e.sh}  shellcheck + жизненный цикл (build/run/install/uninstall/sign/verify)
```

Принцип: один модуль — одна ответственность. Детект платформы, вывод и строки — каждый в одном месте,
не размазаны (в отличие от оригинала с тройным дублированием арх-`case` и 130 строковыми глобалами).

Команды CLI: `build`, `make`, `run`, `list`, `info`, `uninstall`, `cache`, `sign`, `verify`,
`version`, `help`.

## Поток сборки (`bs build`, lib/pack.sh)

1. Разобрать аргументы (`<src>`, `-o`, `--gzip`).
2. `manifest::parse` + `manifest::validate` (обязательные поля, безопасное имя).
3. Проверить, что `exec` существует в исходнике. Бандлинг (если включён) требует нативной арх.
4. Скопировать исходник в staging (`mktemp`, не мутируя оригинал; права и симлинки сохраняются;
   артефакты сборки исключаются). Выставить exec-бит.
5. Опц. `bundle::collect`: `ldd` -> копировать не-системные `.so` в `staging/lib`.
6. Вычислить **`build_id`** (контент-хэш дерева) и записать в манифест.
7. Упаковать staging в `tar.xz` (фолбэк `gzip`) воспроизводимо (GNU tar: `--sort=name`, owner 0,
   mtime `SOURCE_DATE_EPOCH:-0`). Члены — в корне архива (без `./`).
8. `cat template/stub.sh + маркер + payload > out.bs`, `chmod +x`. Опц. `sha256` рядом.
9. Очистка temp по `trap ... EXIT`.

## Рецепты (`bs make`, lib/recipe.sh)

Декларативный рецепт описывает, **откуда** взять готовый бинарь: `source_type` = `tar` / `zip` / `deb`
(`ar`, без dpkg) + `source_url` + `source_sha256`. `bs make`: скачать (контент-адресуемый кэш скачек по
sha256, `BS_NO_FETCH_CACHE=1` отключает) → проверить сумму → распаковать в staging → дальше как
`bs build`. Компиляцию из исходников не делаем (это на пользователе/CI) — пакуем готовое.

## Поток раннтайма (template/stub.sh — внутри каждого `.bs`)

Stub самодостаточен: package работает только с coreutils + tar (+ xz/gzip).

1. Найти payload по строке-маркеру `__BS_PAYLOAD__` (`grep -m1`, кэш смещения/magic в глобалах —
   один скан), `tail -n +N`.
2. Определить сжатие по magic-байтам (`fd37…` xz, `1f8b` gzip) и распаковать **явно** —
   этот tar не автодетектит сжатие из пайпа.
3. Прочитать встроенный `manifest` (только нужный член через `tar -xO`), распарсить как данные.
4. Арх/ОС-страж: если пакет не под текущую `uname -m/-s` — внятный отказ (обход `BS_NO_ARCH_CHECK=1`).
5. Режим:
   - **run** (дефолт): распаковать в XDG-кэш идемпотентно (ключ — `build_id`, см. ниже), выставить
     `PATH`/`LD_LIBRARY_PATH`, опц. `isolate_home`, `exec` приложение;
   - **--install [--system]**: разложить по XDG (user) или `/opt`+`/usr/local` (system),
     сгенерировать лаунчер и `.desktop` из манифеста (+ иконки hicolor, mime, man, completion),
     записать список путей в `<appdir>/.bs-files`;
   - **--uninstall**: прочитать `.bs-files`, удалить, снести каталог приложения;
   - **--extract / --info / --check / --help**.

## Реестр установленного (lib/installed.sh)

Детект по паре `manifest` + `.bs-files` в data-каталоге — без отдельной БД и без исходного `.bs`.
`bs list` перечисляет установленное (имя/версия/scope/путь), `bs info <name>` — метаданные и список
файлов, `bs uninstall <name> [--system]` — снятие по `.bs-files`. Чужие каталоги в `/opt` не трогаем.

## Модель версий и пин пакета

Четыре независимые «версии», у каждой своя роль:

| Что | Где | Роль |
|---|---|---|
| `format_version` | манифест + шапка (план: ROADMAP F1.1) | контракт формата; рантайм-страж отвергает пакет новее, чем умеет |
| `version` пакета | манифест, имя файла `name-version-arch.bs` | версия приложения; ключ реестра/апгрейда |
| `build_id` | контент-хэш дерева, пишет сборщик | ключ кэша распаковки; идемпотентность |
| версия `bs` (CLI) | `bs version` | инструмент; в пакет не вшивается |

**Пин — на трёх уровнях:**

1. **Пакет неизменяем.** Один `.bs` = один билд: stub + маркер + `tar.xz`. «Пин версии» для
   пользователя = просто держать нужный файл. Ничего не тянется из сети на запуске, ничего не мутирует.
   (Контраст с оригиналом, который sed-ом переписывал собственный исходник — Музей, Зал 1.)

2. **Кэш по `build_id` (контент-хэш).** Распаковка в `$XDG_CACHE_HOME/installer-bs/<name>-<version>/`
   кэшируется по контент-хэшу дерева:
   - пересборка того же `name-version` с тем же содержимым → тот же `build_id` → кэш переиспользуется;
   - изменилось содержимое → новый `build_id` → **атомарное** переизвлечение (temp + `rename`, без
     гонки первых запусков и без stale-кэша).

   Значит «та же версия» никогда не означает «молча другой бинарь»: подмена контента видна по `build_id`.

3. **GUI пиннит ядро через релиз.** Installer-BS Manager живёт в `apps/installer-bs-gui/` (монорепо) и
   при сборке **бандлит ядро из того же дерева**. Пин — это **тег релиза GUI** (`bs-gui-X.Y`): его
   `.bs`-ассет иммутабелен и несёт ровно ту версию `bs`+формата, что была в дереве на момент тега
   (провенанс = тег/коммит). Релизы GUI и ядра независимы; пользователь качает один файл со страницы
   Releases, без клонирования репо.

**Апгрейд установленного** (`--install` поверх старой версии): прежние файлы снимаются по `.bs-files` +
payload целиком; `home/` (изолированные данные при `isolate_home`) переживает. Откат = поставить
прежний `.bs`. Никакого in-place патчинга.

## Подпись и провенанс (lib/sign.sh)

Три независимых, честно названных слоя — не «несколько проверок ради театра» (Музей, Зал 1):

- **`sha256` sidecar** (`.sha256` рядом) — от битой докачки, **не** крипто-подлинность;
- **OpenPGP `.sig`** (`bs sign` / `bs verify`) — подлинность; ключи — в проектном keyring
  (`bs trust` / TOFU — план ROADMAP F1.2), не в глобальном GPG;
- **`bs --check`** — гоняет payload через декомпрессор (CRC контейнера) без вшитого хэша. Вшитый sha256
  отвергнут как самореференс (= MD5-театр оригинала).

## Как расширять

- **Новая строка UI:** добавь ключ в `locales/en.sh` (и `ru.sh`), используй `i18n::t key [args]`.
  Английский — обязательная база; недостающий перевод мягко падает в английский.
- **Новая платформа (например, FreeBSD):** добавь `lib/platform/freebsd.sh` с теми же функциями,
  что и `linux.sh`. Не вставляй `if FreeBSD` в тело других функций.
- **Новое поле манифеста:** опиши в [`docs/PACKAGE-FORMAT.md`](PACKAGE-FORMAT.md); парсер
  принимает неизвестные ключи (forward-compat), читай через `BS_MANIFEST[key]` / `MF[key]`. Если поле
  меняет контракт рантайма — это bump `format_version` (см. выше).
- **Перед PR:** прогони `tests/lint.sh` (shellcheck) и `tests/e2e.sh`.
